# Snap Spend — Decisions

Decisions already made. Don't re-litigate; add new entries at the bottom with a date.

## 2026-11-26 — Kickoff / Phase 0

### Platform & tooling
- **D1. Expo SDK 58** (expo 58.0.26, React Native 0.88.1, React 19.3, TypeScript 6.0). New Architecture is on (default).
- **D2. `minSdkVersion` = 24**, the React Native default. Not overridden in `app.json`.
- **D3. `android/` and `ios/` are not committed** (Continuous Native Generation). Native config lives in `app.json` and config plugins; the folders are regenerated by `npx expo prebuild` / `npx expo run:android`.
- **D4. Android only.** The template's web-only helpers (`useClientOnlyValue`) were removed. Web and iOS config is left in `app.json` untouched but never tested.
- **D5. Template folders moved under `src/`** (`src/components`, `src/constants`) so `@/` → `src/` matches the CLAUDE.md folder layout.
- **D6. Line endings are LF** everywhere (`.gitattributes` + Prettier `endOfLine: lf`). This matters for the byte-for-byte golden tests.
- **D7. TypeScript 6 requires explicit `types`**: `tsconfig.json` sets `"types": ["jest"]`. Add more there if a global type package is needed.
- **D8. JDK 17 for Android builds.** The machine has JDK 25 as default. React Native's Gradle build targets JDK 17, so builds use a JDK 17 via `JAVA_HOME` (see PROGRESS.md / README for setup).
- **D9. Device testing uses wireless debugging** (`adb pair` / `adb connect` over Wi-Fi), not USB. Both phones support it (Android 11+).
- **D10. No AI attribution in git** (no `Co-Authored-By` trailers). Commits are authored by the owner only.

### Native module risk check
- **D11. `react-native-document-scanner-plugin@2.0.4`** ships a `codegenConfig` (New Architecture TurboModule) and an Expo config plugin, and wraps `play-services-mlkit-document-scanner:16.0.0`. Considered compatible with SDK 58; to be confirmed by a real build in Phase 4. Fallback if it fails: gallery import via `expo-image-picker` only, recorded as a blocker.
- **D12. ML Kit document scanner requires Google Play services** on the device. Both target phones have them. It will not work on an emulator image without Google Play.

### Spec ambiguities resolved
- **D13. Which total the Daily Log prints per receipt.** `scanned` receipts print `computedTotal` (items − discounts + charges), so each line is arithmetically consistent with its tokens, which is what the golden tests show. `total_only` / `manual` print `printedTotal`. The Review screen's sanity check is where any mismatch with `printedTotal` gets fixed before saving.
- **D14. `points` adjustments (SPAR Repont)** do not change `computedTotal` and are **not printed** in the Daily Log (SPEC §6 only defines discount and charge tokens). They are stored and shown on the Review / Detail screens.
- **D15. Receipt order within a day:** by `time` ascending, receipts with no `time` after timed ones, ties broken by `createdAt`.
- **D16. qty > 1 pcs with `unitPrice` null:** the Daily Log prints `round(lineTotal / quantity)` as the unit price.
- **D17. Non-integer pcs quantity** (rare, e.g. 1.5 pcs) prints the quantity as-is with `.` decimal (`1.5Db×…`).
- **D18. Discount/charge tokens** use the separator ` − ` / ` + ` in place of the item ` + ` separator, exactly as in golden test 3 (`… Bio bag 19Ft − Clubcard discount 100Ft …`).
- **D19. Duplicate guard** = same canonical store (after aliases) + same date + same `printedTotal`. It warns, never blocks.
- **D20. Dates and "today"** use the device's local time zone. Stored as ISO `YYYY-MM-DD` text.
- **D21. IDs** are UUID v4 strings (generator chosen in Phase 2).

### Open (decide when the phase arrives)
- **O1. Items tracker tab.** CLAUDE.md lists tabs index, scan, log, insights, settings, but SPEC §2.5 adds an Items tracker. Decide in Phase 6 (proposal: add an `items` tab, 6 tabs total). Resolved: D63.
- **O2. Default Gemini model id.** Check the Gemini API docs for the current stable Flash model in Phase 3. Resolved: D48.
- **O3. Other AI providers (owner's idea, 2026-11-28, not scheduled).** Keep the option to read receipts with providers other than Gemini: **OpenRouter** or **OpenCode** as a single gateway, giving access to DeepSeek, GLM (Zhipu), Kimi (Moonshot) and others. Gemini stays the only provider for now. When this is picked up:
  - The receipt prompt and response format already live in their own file (`src/lib/receiptPrompt.ts`), and every answer goes through the same zod check (`validateReceipt`). A new provider only needs its own request/response code.
  - OpenRouter and OpenCode use the OpenAI-style "chat completions" format. Images go in as `image_url` data URIs, and JSON output uses `response_format` (support varies by model).
  - The chosen model **must read images**. Several DeepSeek / GLM / Kimi models are text-only, so check each model's image support when this is picked up.
  - Settings would get a provider picker, a secure-store key per provider, and a model name per provider.

## 2026-11-26 — Phase 1

- **D22. Phase 1 started before Phase 0 was finished**, at the owner's request. The device-build item of Phase 0 stays open and is done when the phone is paired. Phase 1 needs no device.
- **D23. `formatDailyLog` output** joins lines with `\n` and has no trailing newline. No receipts gives `''`, even with GRAND TOTAL on.
- **D24. Daily Log totals are computed from items and adjustments** when the log is built, not read from the stored `computedTotal` column, so an edited item always shows up in the log.
- **D25. Money helpers.** `formatAmount(n)` gives `3.894` (used inside the log); `formatFt(n)` gives `3.894 Ft` (UI). Non-integers are rounded. `parseHuf` returns `null` for anything it can't read. Spaces and `.` followed by groups of exactly 3 digits are thousands separators, `,` is the decimal separator, and a lone `.` with other than 3 digits after it is a decimal point (`12.5`). Decimals are rounded to whole forints.
- **D26. Sanity check passes** when computed equals printed, or when printed + redeemed points equals computed (the receipt printed the total after Repont, SPEC §5).
- **D27. Schema leniency.** The zod schema rejects wrong types, non-integer money, bad units, quantity ≤ 0, negative adjustment amounts and invalid dates. It quietly fixes harmless things: missing optional fields → `null`, `HH:MM:SS` → `HH:MM`, masked card number → last 4 digits (or `null`), blank strings → `null`. `lineTotal` may be negative (returned items). Unknown categories are not rejected; `normalizeReceipt` maps them to `Other`.
- **D28. Category is named `Pantry`.** The "(canned, rice, oil, spices)" in SPEC §3 is a description, not part of the name.
- **D29. `normalizedKey`** = English name + size label, lowercased, whitespace collapsed. The size isn't appended again if the name already ends with it.
- **D30. `@types/node`** is in `tsconfig.json` `types` so tests can read `docs/SPEC.md`. A test checks that the golden fixtures match the SPEC §6 blocks exactly.
- **D31. Money on app screens is `3,894.00 Ft`** (owner's choice, replaces the `formatFt` part of D25): `,` thousands separators, always `.00`, ` Ft` suffix. **The Daily Log is unchanged** and keeps the SPEC §6 style (`3.894 Ft`, `239Ft`) via `formatAmount`. `parseHuf` now reads both styles: if `.` and `,` both appear, the last one is the decimal separator; if only one appears, it groups thousands when every group after it has exactly 3 digits (`1,059`, `1.059`), and otherwise a single one is a decimal point (`12.5`, `1059,4`).
- **D32. Native code is built for `arm64-v8a` only**, using the local config plugin `plugins/withArm64Only.js`, which sets `reactNativeArchitectures` in `gradle.properties` on every prebuild. Both target phones are arm64, and this cuts native compile time by about 75%. The release APK is arm64-only too. To support an x86 emulator or an old 32-bit phone, remove the plugin from `app.json`.
- **D33. The Android SDK is installed without Android Studio's wizard**: Google's standalone platform-tools + command-line tools in `%LOCALAPPDATA%\Android\Sdk`, plus `platforms/android-37.0`, `build-tools;37.0.0`, `ndk;27.1.12297006` and `cmake;3.22.1` through the `android sdk install` CLI. Android Studio is installed but not needed for builds.
- **D34. `npm run android` runs `expo run:android`** (Expo prebuild changed this script). It builds the dev client, so it replaces the old `expo start --android` script, which only made sense with Expo Go.
- **D35. CMake 3.31.6 for native builds on Windows.** The SDK default CMake 3.22.1 ships ninja 1.10.2, which can't use Windows long paths, so Reanimated's C++ build failed (`ninja: error: mkdir(...): No such file or directory`) even with `LongPathsEnabled=1`. CMake 3.31.6 ships ninja 1.12.1, which can. The local config plugin `plugins/withCmakeDir.js` writes `cmake.dir` into `android/local.properties` on prebuild, if that CMake is installed in the SDK. Install it with `android sdk install "cmake/3.31.6"`.

## 2026-11-26 — Phase 2

- **D36. IDs come from `expo-crypto`'s `randomUUID()`** (resolves D21). Jest replaces it with Node's `crypto.randomUUID` (`jest.setup.ts`).
- **D37. SQL columns are snake_case** (`printed_total`); TypeScript fields stay camelCase as in SPEC §4. `adjustments` also cascade-delete with their receipt. `PRAGMA foreign_keys = ON` runs when the database is opened, because SQLite leaves it off by default.
- **D38. Repository functions take the database as a parameter** (`AppDatabase` = any synchronous drizzle SQLite database with our schema). The app passes expo-sqlite; tests pass an in-memory **sql.js** (WebAssembly) database with the real drizzle-kit migrations applied, so queries, transactions and cascades are tested for real in Node.
- **D39. `updateReceipt` replaces the whole receipt**: fields, items and adjustments, in one transaction, keeping `createdAt`. The Review and Detail screens edit everything at once, so there are no partial updates.
- **D40. Item search runs in JS, not SQL**, because SQLite's `LIKE`/`lower()` only fold ASCII. It ignores case and accents (`turo` finds `TÚRÓ`), and every word in the query must appear in the English or original name.
- **D41. `listItems` sorting.** Date and amount default to descending; name, store and category default to ascending. Ties are broken by newest date, then time, then position on the receipt.
- **D42. Sample data is loaded manually, never automatically.** A dev-only panel on Tab Two (`__DEV__` only, so not in release builds) loads or clears it. Sample receipts carry the note `[sample data]`, so clearing never touches real receipts. The golden-test receipts moved to `src/db/seedData.ts` and are shared by the seed and the golden tests.

## 2026-11-26 — Sync plan (owner's choice)

- **D43. Two-phone sync will be automatic cloud sync** (owner chose "option 3"), added as **Phase 9** after the app works end to end. Each phone keeps its own SQLite as the store it reads and writes, so the app stays fully usable offline. Changes sync to a cloud Postgres (**Neon**) in the background when there's internet. Database credentials never ship inside the APK: sync goes through either a small API we host or a ready-made SQLite↔Postgres sync service. Which one is chosen in Phase 9, after checking current Expo + drizzle support. Sign-in and conflict handling (last write wins by `updatedAt`, as the starting point) are also designed then.
- **D44. Preparing for sync now:** receipts get **soft deletes** (`deletedAt` timestamp, hidden from every list and total) instead of being erased, so a delete on one phone can sync to the other. This is done at the start of the next session, before the rest of Phase 3. The Phase 8 JSON backup import **merges** by receipt id + `updatedAt` instead of replacing.
- **D45. Receipt images: keep the compressed copy only** (owner's choice). The app saves the same compressed JPEG it sends to Gemini (long edge ≈ 1600 px, quality ~0.7, roughly 200–400 KB per page) in its document directory, not the full-size camera original (3–5 MB). That copy is enough for the Receipt detail screen and for "Retry with Gemini" later. This replaces "copy originals into app storage" in the Phase 4 checklist.
- **D46. Image retention setting** (Phase 8): Settings → "Delete receipt images older than: Never (default) / 6 months / 1 year". Only the image files and `imagePaths` are removed; the receipt and its items stay. Images are not part of the Phase 9 database sync; whether to sync them (it needs separate file storage, not Neon) is decided in Phase 9.

## 2026-11-28 — Phase 3

- **D47. How soft delete works** (implements D44). `receipts.deleted_at` (epoch ms, null = live) is added by migration `0001_soft_delete`. `deleteReceipt` sets `deletedAt` and `updatedAt` to the same time (so last-write-wins sync sees the delete as the newest change) and keeps the receipt's items and adjustments. Deleting an already deleted receipt returns `false` and leaves its timestamp alone. `updateReceipt` treats a deleted receipt as not found. Every read goes through the exported `notDeleted` condition: `listByDateRange`, `listItems`, the dev panel count, and so every Daily Log total. There is no undelete or purge yet. The dev-only `clearSampleData` still **hard**-deletes sample rows (deleted ones too), because sample data is never synced.
- **D48. Default Gemini model is `gemini-3.8-flash`** (resolves O2). It was the current stable Flash model on 2026-11-28 (GA since 2026-09-02), with image input and structured output. `gemini-3.7-flash` and older are deprecated. The model name stays editable in Settings, and "Test key" shows a clear error if a model isn't found. Confirmed 2026-11-28: the API's model list shows `gemini-3.8-flash` supports `generateContent`, and a test call returned 200. It also returned 503 "high demand" once earlier that day, so the receipt retry on 5xx matters.
- **D49. Where settings live.** The API key is in `expo-secure-store` (encrypted with the Android Keystore). The model name isn't secret, so it's in `expo-sqlite/kv-store`, which needs no extra native module and is separate from the app's drizzle tables, so it won't be synced in Phase 9. The screen only ever holds the masked key (`••••••••abcd`); the full key is read from the secure store right before a request. Pasted keys are stripped of whitespace. A blank model name or a pasted `models/` prefix is normalised.
- **D50. Gemini client returns typed errors.** `src/lib/gemini.ts` sorts failures into `no_key`, `bad_key` (400 with API_KEY_*, 401, 403), `model_not_found` (404), `rate_limited` (429), `server` (5xx), `bad_request`, `network`, `timeout` and `bad_response`, each with a friendly message plus the API's own message as `detail`. The key is sent only in the `x-goog-api-key` header and is scrubbed from any error text. "Test key" sends one short text prompt with a 30 s timeout (an overloaded model can take ~20 s just to return 503) and no retry; any HTTP 2xx JSON reply counts as a pass.
- **D51. Second dev machine: Linux.** Builds also run on a Debian PC: Android SDK in `~/Android/Sdk` (platform 37.0, build-tools 37.0.0, NDK 27.1.12297006, CMake 3.31.6) and JDK 17 from SDKMAN (`~/.sdkman/candidates/java/17.0.10-tem`). This PC has its own adb pairing with the phone.
- **D52. Dev-only `.env` key** (owner's idea). `EXPO_PUBLIC_GEMINI_API_KEY` in a local `.env` (gitignored; `.env.example` is committed as a template) is used **only in development builds** and **only when no key is saved in Settings**. A key saved in Settings always wins, and Settings labels a `.env` key and hides "Remove" for it. The variable is read as `__DEV__ ? process.env.EXPO_PUBLIC_GEMINI_API_KEY : undefined`, so release builds drop it. Checked on 2026-11-28 with a marker value: the release bundle (`expo export:embed --dev false`) had 0 copies, and the Metro dev bundle had 1. Metro reads `.env` only at start-up, so restart it after editing the file. The Phase 8 release step re-checks the bundle for the key.
- **D53. Negative adjustment amounts are accepted and stored as positive** (changes part of D27). A real Gemini 3.8 Flash test on 2026-11-28 returned the Repont line as `amount: -100`, copying the receipt's `-100`. The SPEC prompt doesn't say amounts must be positive, so `validateReceipt` now keeps the size and drops the sign; `type` says whether it's a discount, charge or points. Non-integer amounts are still rejected.
- **D54. Receipt extraction behaviour** (`extractReceipt` in `src/lib/gemini.ts`). The request is the SPEC §5 prompt with the category list filled in, plus one `inline_data` JPEG per page, `temperature 0.1`, `responseMimeType: application/json` and the SPEC `responseSchema`. Gemini accepted this as-is in the real test.
  - Timeout is 60 s. After a 429 or 5xx it waits 2 s and retries once. Network failures, timeouts and 400s are not retried, because the user has a Retry button.
  - "Thought" parts in the answer are ignored. A blocked prompt or a safety stop gives `blocked`, and no text gives `empty_response`.
  - Unparseable or invalid JSON gives `invalid_receipt` with the zod issues and the raw answer text, so the Review screen can offer manual edit or Retry. If the answer stopped at the token limit, the message says it was cut off.
  - Store aliases and category mapping are not done here; `normalizeReceipt` still does them.

## 2026-11-28 — Phase 4

- **D55. Receipts have an optional `category` column** (migration `0002_receipt_category`). SPEC §2.3 gives manual expenses an optional category, but only items had one. It's used by `manual` / `total_only` entries and is `null` for scanned receipts, whose items carry their own categories. Insights (Phase 7) should use it for receipts with no items.
- **D56. Which `kind` a saved receipt gets.**
  - Add expense: `total_only` when a slip photo is attached, otherwise `manual`.
  - Review: a `scanned` receipt whose items were all removed is saved as `total_only`.
- **D57. Daily Log numbers use `,` thousands separators** (owner's request, 2026-11-28; replaces the `.` rule in SPEC §6 and the Daily Log part of D31). Examples: `1,946 Ft`, `3,894 Ft`, `1,398Ft`. SPEC §6 and its three golden tests were updated to match, and they still pass byte for byte. Decimal points are unchanged (`1.294Kg`, `2.8%`). App screens keep `3,894.00 Ft` (D31).
- **D58. Fonts: Google Sans (UI) and Google Sans Code (Daily Log)**, owner's request: "the font used in Google Keep". Both are SIL OFL 1.1, from `@expo-google-fonts/google-sans` and `@expo-google-fonts/google-sans-code`, loaded with `expo-font` (no native rebuild).
  - Android doesn't make bold or medium versions of custom fonts by itself, so the themed `Text` picks the family for each weight (`fontForWeight`).
  - Inputs and navigation headers and tabs use Google Sans too. Space Mono was removed.
- **D59. How the scan queue works.**
  - The queue lives in memory; unsaved jobs are lost if the app is closed. Saved receipts are in SQLite.
  - Jobs run one at a time, oldest first: compress, then read with Gemini.
  - One scanner session is one receipt with up to 10 pages. Each gallery photo is its own receipt, up to 20 per batch.
  - Pages are decoded at most 3200 px, resized to a 1600 px long edge and saved as JPEG at 0.7.
  - Scanner originals (our temporary files) are deleted after compressing. Gallery photos are never touched.
  - On Save, the compressed copies go to `<document>/receipts/<receiptId>/page-N.jpg` before the database insert. They're removed again if the insert fails.
  - Camera and microphone permissions are removed from the app; the ML Kit scanner runs inside Google Play services.
- **D60. Shared UI pieces** live in `src/components/ui.tsx` (palette, button) and `src/components/form.tsx` (field, banner, segmented control, picker). `ReceiptForm` is shared by Review and Add expense.
- **D61. Stricter prompt rules** (owner's request, 2026-11-28; SPEC §5 prompt updated, `receiptPrompt.ts` mirrors it).
  - **Deposits are never items.** "visszaváltási díj" / "visszav. díj" / "betétdíj" / DRS lines (ALU, PET, üveg) are `charge` adjustments labelled "Deposit", linked to their product. Returned-bottle vouchers ("visszaváltási jegy", "göngyöleg") are `discount` "Deposit refund".
  - **Repont / "pont beváltás" is always `points`.** The first version of the refund rule listed bare "visszaváltás", and Gemini then read "REPONT BEVÁLTÁS" as a deposit refund. The wording was narrowed to stop that.
  - **Amounts are copied exactly as printed.** In a test receipt whose lines didn't add up, Gemini had silently changed an item from 839 to 789 to match the total. Now it keeps 839 and explains the mismatch in `notes`; the Review screen shows the notes and an amber sanity banner.
  - Checked against the real API on 2026-11-28 with `gemini-3.8-flash` and `gemini-3.6-flash`: two test receipts (SPAR with Repont; TESCO with two deposits, a voucher and a deliberate total mismatch) came back correct on both models.

## 2026-11-28 — Phase 5

- **D62. Daily Log ranges.**
  - Presets: **Today**, **This week**, **This month**, **Last month**, plus **Custom**. SPEC §2.4 lists the last three; Today was added for quick checks.
  - Weeks start on **Monday** (Hungary). "This week" and "This month" run up to today; "Last month" is the whole previous month.
  - Custom uses the Android system calendar (`DateTimePickerAndroid`, no future dates). A range picked backwards is swapped.
  - The GRAND TOTAL switch resets to the SPEC default whenever the range changes: on for more than one day, off for a single day. The user can still toggle it.
  - The log refreshes by itself when receipts change, using a live query on the receipt count and latest `updatedAt`. It's the Daily Log tab (`app/(tabs)/log.tsx`). The dev panel on Tab Two still exists until Phase 7 replaces the template tabs.

## 2026-11-28 — Phase 6

- **D63. Tabs** (resolves O1, owner agreed). Six tabs in the end: Home (`index`), Scan, Daily Log, Items, Insights, Settings. In Phase 6 the template "Tab Two" became **Items** (`app/(tabs)/items.tsx`); Home and Insights come in Phase 7. The dev sample-data panel moved to the bottom of Settings, still `__DEV__` only, and its Daily Log preview was dropped because the Daily Log tab replaces it.
- **D64. Items list behaviour.**
  - SQL does the date, store and category filters and the sort. Text search runs in JS on top, so it can ignore accents (D40) and doesn't re-run the query on every keystroke.
  - Date presets are All time / This week / This month / Last month / Custom (calendar), using the same range rules as the Daily Log (D62).
  - Store choices come from `listStores` (live receipts, A–Z); categories are the default list.
  - The footer sums the line totals of the rows shown. Receipt-level discounts, charges and points aren't items, so they're not included.
  - Tapping the active sort button flips its direction. Defaults: date and amount newest/largest first; name, store and category A–Z (D41).
- **D65. Price history rules.**
  - A product is all items sharing a `normalizedKey`.
  - Unit price is the printed `unitPrice`, else line total ÷ quantity (rounded).
  - Returned items (negative lines) are skipped. If a product was bought both per piece and per kg, only the unit of the latest purchase is charted.
  - "Cheapest" is the lowest unit price; the most recent purchase wins a tie.
  - The chart's y-axis starts near 80% of the lowest price so changes are visible.
- **D66. `useReceiptsVersion`** is a shared live-query signal (receipt count + latest `updatedAt`). Daily Log, Items and Price history use it to refresh themselves after any save, edit or delete.

## 2026-11-28 — Phase 7

- **D67. Category breakdown adds up to the total.** Item line totals count under their category. Receipts without items count under their receipt `category` (D55), or Other. Receipt-level discounts and charges go in one net **"Discounts & charges"** row, so every month's categories sum to the month total (points still don't count, D14).
- **D68. What the Insights screen covers.**
  - The 12-month bar chart ends with the current month.
  - Store, category and card totals are for the **selected month**; the default is the current month.
  - **Top 10 items** are for the **last 12 months**, ranked by number of purchases (receipt lines), with ties broken by money spent. Each opens its price history.
  - Breakdowns are horizontal proportion bars instead of pie charts, which are easier to read on a phone. Cards are shown as `•••• 1234`; receipts without a card are grouped as "No card".
- **D69. Receipt detail.**
  - It opens from Home's recent receipts.
  - Editing uses the shared `ReceiptForm`, and Save calls `updateReceipt`. The saved `imagePaths` are passed through unchanged, because the form doesn't edit photos.
  - The duplicate warning leaves out the receipt being edited (`excludeId`).
  - Delete is a soft delete (D44). Its photos stay on the phone until the retention setting (D46) removes them.
  - The zoom viewer uses gesture-handler + reanimated: pinch 1–6×, drag when zoomed, double-tap to zoom or reset, and page arrows for multi-page receipts. The app root is wrapped in `GestureHandlerRootView`.
- **D70. Template leftovers removed:** the info modal, `EditScreenInfo` and `StyledText`. Home replaces "Tab One". Tabs: Home, Scan, Daily Log, Items, Insights, Settings (D63).


## 2026-11-28 — Phase 8

- **D71. Excel export instead of CSV** (owner's choice: .xlsx opens directly on phones).
  - `src/lib/xlsx.ts` is a small writer of our own: Office Open XML, zipped with `fflate` (pure JS, MIT). No SheetJS / exceljs, which are large and mostly unused here.
  - Features: several sheets, a bold frozen header with filter buttons, column widths, real date cells (`dd/mm/yyyy`), money as `#,##0`, quantities as `0.###`. Text uses inline strings, and characters XML forbids are stripped.
  - Two sheets, oldest first. **Items**: date, time, store, item, original name, size, qty, unit, unit price (printed, else total ÷ qty), total, category, card. **Receipts**: date, time, store, type, total, printed total, item count, discounts, charges, points, card, category, note.
  - Checked by opening generated files, including one exported on the phone, with LibreOffice.
  - Files are written to the cache directory and shared with `expo-sharing`, because React Native's `Share` can only send text on Android.
- **D72. JSON backup format and merge.**
  - Format: `{ format: "snapspend-backup", version: 1, exportedAt, receipts[], storeAliases[] }`. Each receipt is its full row, including `deletedAt`, plus its items and adjustments with their ids.
  - Soft-deleted receipts are included so deletes travel with the backup. **Photos are not included**; the Receipt detail screen only shows photos that exist on this phone.
  - Import is checked with zod (whole-forint money, known enums). It rejects non-backups and files from a newer version.
  - Merge happens in one transaction (D44): a missing receipt is added; an existing one is replaced only if the backup's `updatedAt` is newer, children included; otherwise it's left alone. Store aliases are added when missing; local ones win.
  - Import uses `File.pickFileAsync` from `expo-file-system`, so no extra native module is needed.
- **D73. Category list and store-name editors.**
  - Categories now live in a `categories` table (name, position), seeded with the SPEC §3 defaults by migration `0003_categories`, which also adds the default INTERSPAR → SPAR (Interspar) alias. Before this, nothing read the `store_aliases` table; every screen used the built-in defaults.
  - Each list has its own screen, opened from Settings → Lists: **Categories** (add, rename, delete, move ↑↓) and **Store names** (add, edit, remove).
  - A new category goes just before "Other". **"Other" can't be renamed or deleted**, because unknown categories from Gemini fall back to it.
  - Renaming a category also renames it on every item and receipt-level category. Deleting moves those to "Other", after a confirmation that shows how many items it affects. The affected receipts get a new `updatedAt`, so the change wins a backup merge or a sync (D44).
  - After saving a store name, if any saved receipts still use the printed name, the app asks whether to rename them too. Matching ignores capitals and extra spaces, the same rule `applyStoreAlias` uses. Removing a store name never changes saved receipts.
  - The live lists go to the Gemini prompt (read when each scan starts), the Review, Add expense and Receipt detail forms (validation, duplicate check, category pickers) and the Items category filter.
  - The JSON backup has an optional `categories` array (still version 1, so older files import). On import, missing categories are added before "Other"; the local list and order win. Categories used by imported items are added even if the file's list doesn't have them.
- **D74. How photo retention works** (implements D46).
  - The setting is **per phone**, because photos aren't synced. It's stored in `expo-sqlite/kv-store` as `image_retention`, next to the model name (D49). An unknown or missing value means Never.
  - Age is by the **receipt's date**, not when it was scanned. "6 months" and "1 year" are calendar months back from today, clamped to the end of shorter months. A receipt dated exactly on the cutoff keeps its photos.
  - It runs once per app launch, after the database migration, and again right after the setting changes. A stricter setting first asks for confirmation, showing how many receipts' photos and how much space will go. A looser setting, or one with nothing to delete, saves straight away.
  - The photo files and the receipt's `receipts/<id>` folder are deleted and `imagePaths` is set to null. Receipts, items and totals stay.
  - Soft-deleted receipts follow the same age rule, so their photos are eventually removed.
  - `updatedAt` is **not** changed, because photos are this phone's own data: removing them isn't an edit that should win a backup merge or a sync.
  - Settings shows how much space receipt photos use on the phone.
- **D75. Theme and error states.**
  - The theme **follows the system** (SPEC §7): `userInterfaceStyle: automatic`, and there's no in-app switch.
  - The navigation theme's background is set to the themed View background (`#fff` / `#000`). Before, light mode showed white bands on the navigation theme's grey. Checked every tab and the pushed screens in both themes on the phone.
  - Any screen that throws while rendering, such as a failed database read, shows a themed **"Something went wrong"** page with the message, **Try again** and **Go to Home**. This is the Expo Router `ErrorBoundary` exported from `app/_layout.tsx`. The "Database update failed" screen and the not-found page use the same `ErrorScreen`.
  - Empty and loading states already existed on every screen (Home, Daily Log, Items, Insights, price history, receipt detail, Review, Settings), so they were left as they were.
- **D76. Settings is a grouped list** (owner's request: the long single page looked complicated).
  - The Settings tab shows rounded groups of rows, like Android's own Settings. Each row has an icon, a title and a one-line summary, and opens its own page:
    - **Receipt reading:** Gemini API key & model → `settings/gemini` (key, model, Test key).
    - **Lists:** Categories, Store names (D73).
    - **Data:** Receipt photos → `settings/photos` (choice list, storage used; D74), and Backup & export → `settings/backup` (D71, D72).
    - **Developer:** dev builds only → `settings/developer` (sample data).
  - The summaries refresh each time Settings comes back into view. The API key summary shows only the last four characters, and turns amber when no key is set.
  - The app version comes from the app config and is shown at the bottom.
  - The shared pieces are `SettingsGroup` and `SettingsRow` (`src/components/SettingsList.tsx`). Icons are Material symbols via `expo-symbols`, which the tabs already use, so no new dependency was needed.
  - No in-app theme switch: the owner confirmed following the system theme (D75).
